## 3. Approved Key Decisions Log

1. **Student Provisioning:** Student self-registration with multi-step email verification and administrator identity approval.
2. **Descriptive Answers:** Hybrid approach supporting both browser-typed text and handwritten sheet image/PDF uploads. Provisional defaults (max 3 files, 5 MB/file) kept fully configurable.
3. **Examination Access:** Multi-tier authorization requiring standard student account login PLUS a separate, cryptographically hashed Examination PIN. PIN validity reconciled with entry cutoff and attempt resumption.
4. **PIN Delivery Gate:** Explicit institutional configuration (`EXAM_PIN_DELIVERY_METHOD`), initialized as unconfigured; PIN issuance strictly gated until approved.
5. **Roll Number Architecture:** Configurable pattern-based generator supporting college/GU conventions once finalized (template illustrative only).
6. **PDF Engine:** Pure-Python `ReportLab` for zero-OS-dependency portable admit card generation.
7. **Deadline Enforcement, Ingress Timestamping ($T_{\text{ingress}}$) & Bounded-Processing Consistency Model:** Unified $T_{\text{ingress}}$ terminology across all sections and diagrams; server-authoritative cutoff using high-precision Nginx `$msec` arrival timestamping (`X-Request-Arrival-Time`) unconditionally overwritten by reverse proxy; accepted strictly from configured `TRUSTED_PROXIES`; direct backend access prevented via Unix socket/firewall; mandatory fail-closed behavior on missing/invalid timestamps in production (HTTP 502 `INGRESS_TIMESTAMP_INVALID`); outermost WSGI middleware ingress fallback ($T_{\text{wsgi\_ingress}}$) restricted strictly to development/testing environments (`ALLOW_WSGI_TIMESTAMP_FALLBACK = True`). Option B: Bounded-Processing Consistency Model distinguishing the six lifecycle stages (Physical Arrival $\rightarrow$ Perimeter Ingress Timestamp $\rightarrow$ Complete HTTP Receipt $\rightarrow$ Application Admission $\rightarrow$ Database Transaction Execution $\rightarrow$ Durable Commit). Application Admission Window $W_{\text{admission}} = [\text{start\_time}, \text{official\_end\_time} + \Delta_{\text{drain}}]$ ($\Delta_{\text{drain}} = 15\text{s}$) accommodating socket queues. Coordination strictly through MySQL InnoDB ACID row locks (`SELECT ... FOR UPDATE` on `ExamAttempt`), eliminating distributed TOCTOU race conditions and Redis dependencies. Late write requests arriving after deadline are rejected with HTTP 410 without altering attempt status, preventing premature auto-closure while queued on-time requests traverse socket buffers; auto-closure is deferred strictly to the deadline supervisor worker after the 15-second drain window. Full 16-scenario concurrency analysis documented.
8. **Encrypted Shared-Device Offline Cache & Dual-Track Key Recovery:** Web Crypto API `AES-256-GCM` encryption at rest in IndexedDB with 96-bit random IVs and AAD binding `(student_id, examination_id, attempt_id)`; ephemeral in-memory DEK; zero credentials or PINs stored locally as wrapping keys; Dual-Track key recovery separating Track A (Live Exam Recovery, active `IN_PROGRESS`, $T \le \text{deadline}$, write-enabled) from Track B (Post-Deadline Read-Only Evidence Recovery, finalized attempts within configurable `EXAM_EVIDENCE_KEY_RETENTION_PERIOD`, strictly read-only); diagnostic recovery bundles (`AUDIT_RECOVERY_BUNDLE`) with SHA-256 integrity metadata and server HMACs; institutional kiosk and lab Deep Freeze reboot export rules documented.
9. **Evidence Retention State Machine & Hard Production Gate:** Formal 4-state operational machine (`UNCONFIGURED` -> `CONFIGURED` -> `EXPIRED` / `LEGAL_HOLD`); Hard production activation gate strictly blocking examination scheduling and activation while `EXAM_EVIDENCE_KEY_RETENTION_PERIOD` remains `UNCONFIGURED`; institutional approval requirement (`IsCollegeSuperAdmin`); immutable snapshots captured on `Examination` and `ExamAttempt`; scheduled daily deletion (`purge_expired_evidence_keys`) with security audit logging; legal hold suspension mechanics for active grievance appeals.
10. **Submission Lifecycle, Sequence Model & 16-Scenario Concurrency Model:** Explicit distinction between perimeter arrival $T_{\text{ingress}}$ (`submitted_at`), application admission $T_{\text{admit}}$, and application transaction recording time `transaction_recorded_at` (persisted in `committed_at`). Comprehensive handling of all 16 submission scenarios with exact HTTP response codes (200, 408, 409, 410, 502); transactional row locking (`SELECT ... FOR UPDATE` on `ExamAttempt`) to serialize concurrent autosaves, manual submissions, and deadline supervisor finalization; late manual submissions do not transition attempts to `AUTO_CLOSED_DEADLINE` or trigger grading; Section 13.5 sequence diagram models all branches including on-time autosaves under lock, bounded delay rejections, idempotent submission retries, late submissions without auto-closure, and post-commit asynchronous grading.
11. **XSS Defense-in-Depth:** Acknowledged `HttpOnly` scope (prevents raw cookie theft, but requires defense-in-depth via React JSX escaping, DOMPurify, strict CSP, and backend input validation).
12. **Background Worker:** `Celery` + `Redis` for production batch operations (PDFs, emails, dead-letter supervision), with an abstracted service layer for test execution.
13. **Relational Schema & MySQL InnoDB 8.x Baseline:** 52 normalized tables targeting MySQL 8.x with InnoDB exclusively; character set `utf8mb4` with `utf8mb4_0900_ai_ci`; Django ORM-compatible conventions (signed `BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY`, matching Django default `BigAutoField`, snake_case table and column names); strict SQL mode; 3NF compliance across all entities with 5 formally justified denormalizations for historical immutability and composite FK performance.
14. **Centralized Concurrency, Option B Locking & Full Question-Paper Membership Integrity:** Implementation of Option B Bounded-Processing Consistency Model directly in the relational schema; `attempts_exam_attempt` serves as the centralized row-lock coordination point (`SELECT ... FOR UPDATE`); monotonic answer saving via `attempts_answer.version_sequence`; composite foreign keys `fk_ans_attempt_paper (attempt_id, paper_version_id)` and `fk_ans_map_paper (paper_question_mapping_id, paper_version_id)` referentially guarantee at the MySQL engine level that an answer cannot be submitted for a question mapping from a different paper version; composite foreign keys `fk_ans_map_q (paper_question_mapping_id, question_id)` and `fk_ans_opt_q (selected_option_id, question_id)` enforce question and option ownership; paper version assigned to attempt is strictly immutable; idempotent manual submissions with client UUID4 matching; deadline supervisor finalization respects the 15-second drain window; late submissions rejected with HTTP 410 without altering attempt status.
15. **Transactional Outbox Pattern with Decoupled Dispatcher, Grading Worker & Claim Fencing:** Complete separation of attempt finalization from Celery message broker publication and worker execution into three distinct operations: Operation 1 (Finalization Transaction Tx 7/8 atomically persists attempt state, receipt, and outbox event in `PENDING` status; zero broker network calls inside DB transaction), Operation 2 (Outbox Dispatcher Tx 9A claims batches via `SELECT ... FOR UPDATE SKIP LOCKED`, increments claim-generation fencing token `claim_version`, sets short lease, publishes to Celery broker, and records publication outcome via guarded SQL matching `claimed_by` and `claim_version`; affected-row verification guarantees that a terminal `COMPLETED` state is never overwritten by a delayed or zombie dispatcher), and Operation 3 (Celery Grading Worker Tx 9B acquires attempt lock, verifies finalized state, executes idempotent evaluation, persists scores and audit logs, transitions outbox from any non-terminal state to `COMPLETED`, commits, and sends Celery ack); lock hierarchy standardizes acquiring attempt lock before outbox lock, minimizing lock contention and inversion risks with dispatcher; exhaustive recovery handling across 10 critical concurrency race scenarios and 16 general crash failure scenarios.
16. **Dual-Tier Cryptographic Credential & Realistic PIN Security Model:** Salted PBKDF2-SHA256 password hashes; separately salted PBKDF2 examination PIN hashes with independent 32-byte cryptographic salts (`pin_salt`); honest Shannon entropy acknowledgment for 6-digit numeric PINs ($10^6$ values, $\text{Entropy} = \log_2(10^6) \approx 19.93\text{ bits}$); rejected false claim of hash immunity against offline brute force; multi-layer defense-in-depth enforcement: progressive rate-limiting lockout (5 failed attempts -> 15-minute lock), narrow temporal entry windows ($[T_{\text{start}} - 15\text{m}, T_{\text{start}} + \text{cutoff}]$), single-attempt invalidation, and unconfigured delivery gate; Data Encryption Keys (DEKs) envelope-wrapped under Master KEK via AES-KeyWrap; zero plaintext secrets or PINs stored in MySQL; evidence retention state machine with immutable expiry timestamps and daily automated purging.
17. **Submission Receipt Timestamp Integrity:** Explicit timestamp semantics on `attempts_submission_receipt` separating manual submission ($T_{\text{ingress}}$ in `submitted_at`) from deadline auto-closure (`official_end_time` in `closed_at`); enforced via MySQL CHECK constraint `chk_receipt_status_timestamps`; zero fabrication of manual submission timestamps or client UUIDs for auto-closed attempts.
18. **Private Descriptive Upload Storage Architecture:** Physical handwritten answer sheet photos and PDFs stored outside HTTP webroot in private disk storage; files renamed to random UUID4 identifiers (`uploads_descriptive_upload.file_uuid`) to eliminate path traversal and direct enumeration; ClamAV malware scanning status tracking; streaming access restricted strictly to authenticated Django controller views with role checks.
19. **Two-Tier Answer Payload Validation Architecture:** Tier 1 storage engine enforcement via MySQL CHECK constraint `chk_answer_payload_exclusivity CHECK (selected_option_id IS NULL OR answer_text IS NULL)` mechanically forbidding corrupted hybrid payloads containing both an MCQ option and descriptive text simultaneously, while safely permitting unanswered drafts (`NULL, NULL`), MCQ selections (`opt, NULL`), and descriptive drafts (`NULL, text`); Tier 2 Django application layer validation under row lock validating incoming payload against `question.question_type`: MCQ questions reject typed text and file uploads, while descriptive questions reject option selections and accept typed text, uploaded handwritten sheet files (`uploads_descriptive_upload`), or both.
20. **Production Log Sanitization & Reverse Proxy Trust Boundary (Chunk 03 Round 2 Corrections):** Enforced strict production exception logging policy in `custom_exception_handler` and `SensitiveDataFilter`: raw exception strings (`str(exc)`), arguments, and Python tracebacks (`exc_info`) are completely suppressed from production logs and responses, emitting structured diagnostic metadata (`error_category`, `exception_type`, `sanitized_view`, `request_id`) while clients receive generic HTTP 500 envelopes. Forwarded HTTPS proxy header trust (`SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')`) is fail-closed and disabled by default (`SECURE_PROXY_SSL_HEADER = None`), strictly requiring operator enablement via `TRUST_PROXY_SSL_HEADER=True` with documented verification that Nginx terminates TLS, unconditionally overwrites `X-Forwarded-Proto $scheme`, and mechanically blocks direct client access to Gunicorn/Django via Unix domain socket (mode 0660) or loopback firewall. Corrected misspelled institutional policy test assertion (`INSTITUTIONAL_CONFIG_APPROVED`).
21. **Strict Request-ID Normalization & Ingress Trust Boundary (Chunk 03 Round 3 Corrections):** Implemented centralized request identifier normalizer `normalize_request_id` in `apps.core.exceptions`. Enforces strict regex validation (`^[A-Za-z0-9_-]{1,64}$`) with full-string matching; rejects empty values, whitespace, control characters, newlines/CRLF, Unicode, disallowed punctuation, and strings > 64 chars without truncation. Malformed inputs are discarded and never logged; a fresh server-side UUIDv4 is generated for missing or malformed inputs. Clarified trust boundary: validated identifiers are safe for structured logging but do not authenticate request origin; production reverse proxy (Nginx) must be configured to unconditionally overwrite `X-Request-ID` (`proxy_set_header X-Request-ID $request_id;`). Client-supplied identifiers are strictly untrusted for access control or authoritative security decisions.

## 4. Mandatory Future Acceptance Criteria (Carried Over from Chunk 02 Warnings)

The following warnings from the Chunk 02 Database Architecture Independent Audit (Pass with Warnings) are recorded as mandatory acceptance criteria for future chunks:

1. **Worker-Event Binding (Target: Chunk 11 / Chunk 12):**
   - The Celery grading task must strictly bind to the locked `attempts_exam_attempt` record before inspecting or updating outbox rows.
   - Task identifiers, attempt IDs, and outbox IDs must be mutually validated against persisted database records before grading evaluation begins.
2. **Outbox Claim Fencing & Terminal Immutability (Target: Chunk 11 / Chunk 12):**
   - Outbox dispatcher transitions must use the `claim_version` fencing token and guarded SQL predicates (`status = 'CLAIMED' AND claimed_by = :dispatcher_id AND claim_version = :claim_version`).
   - If `affected_rows == 0`, dispatcher must verify the current state and treat `status == 'COMPLETED'` as obsolete without overwriting.
   - Celery worker must be able to transition the outbox row to `COMPLETED` from any non-terminal state (`PUBLISHED`, `CLAIMED`, `PROCESSING`, `RETRY_PENDING`, `DEAD_LETTER`).
   - Any manual administrative intervention on `DEAD_LETTER` outbox rows must produce an immutable audit trail in `audit_system_audit_log`.
   - Comprehensive live multi-threaded / multi-process MySQL concurrency tests must be executed when outbox execution is authorized.
3. **Institutional Policy Baseline Confirmation (Target: Chunk 05 / Chunk 08):**
   - Authoritative Gauhati University roll number format template must be configured prior to student roll number generation.
   - Official letter grading scale and 10-point formula mapping must be populated in `academics_institutional_config`.
   - Hard production activation gate must prevent examination activation while `EXAM_PIN_DELIVERY_METHOD` or `EXAM_EVIDENCE_KEY_RETENTION_PERIOD` remains `UNCONFIGURED`.
   - Statutory retention schedules for private descriptive upload files (photos/PDFs) must be confirmed and configured before production deployment.
