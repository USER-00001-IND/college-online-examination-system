PROJECT PURPOSE AND CONTEXT
======================================================================

Project name: College Online Examination System

Academic context: Gauhati University FYUGP / NEP 2020 academic context,
intended for college-level use.

The system is intended to support a college’s academic administration
and online examinations. It must be configurable because the exact
college and Gauhati University policies are not fully known or must be
confirmed by the institution.

Core users: 1. Administrator 2. Faculty / Examiner 3. Student

Main purpose: - Configure academic sessions, programmes, departments,
semesters, subjects, paper offerings and subject categories. - Maintain
student and faculty records. - Capture explicit student registrations
for individual paper offerings. - Create examinations and calculate
eligible students from approved registration records. - Allocate
examination roll numbers using a configurable college-prescribed
pattern. - Generate admit cards as PDFs. - Issue a separate examination
PIN in addition to normal student login. - Conduct MCQ and descriptive
examinations. - Allow descriptive answers as typed text and uploaded
images/PDFs. - Autosave student answers and enforce server-side
deadlines. - Auto-mark MCQs and manually evaluate descriptive answers. -
Review, approve and publish results. - Maintain audit logs and secure
private records/files.

This is a college-level system, not a multi-college SaaS platform.

8. DEADLINE AND AUTOSAVE POLICY — IMPORTANT OPEN REVIEW ISSUE
======================================================================

Intended rule: - Server-side time is authoritative. - Client/browser
timestamps are never trusted. - Writes are accepted only if the request
is first received by the trusted ingress/proxy at or before official
end_time. - Requests first received after end_time are rejected even if
the client claims they were composed earlier. - If a request arrived at
the trusted proxy before the deadline but backend processing/database
completion occurs slightly after, it may still be accepted. - No network
transport buffer or offline timestamp may extend the answering period. -
Monotonic sequence numbers/versioning prevent stale autosave
overwrites. - Submission is idempotent and transactionally finalized.

Current architecture Section 13.1 has a critical technical flaw that was
identified by independent review: - It mentions Nginx $time_iso8601 or
$msec, but does not yet precisely specify the correct high-precision
mechanism and trusted-header handling. - It says Nginx overwrites and
forwards X-Request-Arrival-Time, but the exact configuration must
explicitly overwrite any client-supplied header and trust only a
configured trusted proxy. - Do not trust arbitrary X-Forwarded-* or
arrival headers received directly from clients/untrusted proxies. - WSGI
generally cannot observe the original socket-read timestamp after the
WSGI server has parsed the request. The architecture’s phrase “WSGI
entry point (time.time()) upon socket read” is technically inaccurate. -
Correct fallback wording: capture strict server-receipt time at the
earliest reliable server ingress point available; do not claim it is the
physical socket-read timestamp if the WSGI layer cannot observe that. -
The fallback is conservative and may reject a request that physically
reached the machine before deadline but was timestamped later. - No
transport buffer can grant extra answering time.

Required next correction: 1. Specify high-precision Nginx timestamp
(e.g. $msec) for subsecond cutoff. 2. Configure Nginx to overwrite, not
append/trust, client-supplied X-Request-Arrival-Time. 3. Backend accepts
this timestamp only from the configured trusted proxy path. 4.
Direct/untrusted requests cannot provide trusted arrival time. 5.
Correct WSGI fallback statement as described above. 6. Document
conservative nature of fallback and strict cutoff. 7. Ensure diagrams
and text match.

9. OFFLINE ANSWER CACHE — CRITICAL OPEN REVIEW ISSUE
======================================================================

Architecture goal: - Support temporary network loss by caching unsaved
answer data locally. - Cache key scoped to exact
student/examination/attempt:
exam_cache_{student_id}{examination_id}{attempt_id} - Never cache
passwords, PINs, session cookies or authorization tokens. - Use
IndexedDB/localStorage as appropriate. - Sequence each answer update. -
Remove an answer sequence only after explicit server acknowledgement. -
Server rejects any offline answers that first arrive after the official
deadline.

Current architecture Section 13.3 contains a direct contradiction: - It
says unsynchronized answers must be preserved until HTTP 200
acknowledgement. - It also says to purge cache on logout (with a warning
modal). - It also says to purge cache at local TTL/end_time. - These
purge rules can delete unacknowledged answers without server
acknowledgement. A warning or confirmation does not resolve the
data-loss conflict. - It also says offline answers reconnecting after
end_time cannot be accepted, meaning some unacknowledged answers can
never receive a successful acknowledgement under the strict deadline
policy.

Required next correction: 1. Never silently delete unsynchronized
answers merely because the student logs out. 2. Never delete
unacknowledged answers just because local device clock reaches end_time.
3. On logout, protect data from the next user of a shared computer but
preserve it securely for the same authenticated student and exact
attempt. 4. On expiry, mark the cache stale and prevent normal exam
access, but do not silently erase unacknowledged data. 5. Define secure
recovery after logout and exact identity/attempt re-verification. 6.
Define the fate of rejected late-sync data. Since server rejects late
writes, the data cannot be “preserved until server HTTP 200” if no
acknowledgement is possible. 7. Make retention/privacy policy explicit
and institution-approved for orphaned/rejected offline answers. 8.
Synchronized answers may be cleaned after confirmed
submission/auto-close and suitable acknowledgement/cleanup. 9. Avoid
exposing cached answers to the next user on shared college/cyber-cafe
devices. 10. Ensure diagrams and prose agree.

Important unresolved institutional decision: - What retention period and
recovery policy applies to unacknowledged offline answers rejected after
deadline? - This cannot be solved by silently deleting data or by
accepting late writes without institutional approval. - A possible
design to discuss, not assume approved: encrypt and quarantine
unacknowledged local data, bind it to the exact user/attempt, keep it
inaccessible to other users, and apply an explicit institution-approved
retention/review/export/expiry policy. Do not claim this is already
approved.

College Online Examination System — Master Design

  Purpose: This file is the authoritative project instruction and design
  baseline for the AI coding agent.

  Development rule: Work in small chunks. Complete the current chunk,

1. Project Overview

Build a secure, responsive online examination system for a college using
the Gauhati University FYUGP academic structure as the intended academic
context.

The system must support:

-   Multiple programmes, departments, semesters, subjects and papers.
-   Subject-wise student registration and examination eligibility.
-   MCQ and descriptive examinations.
-   Admin, faculty/examiner and student roles.
-   General examination creation by an administrator.
-   Unique examination roll numbers and individual admit cards.
-   PDF admit-card generation and email delivery.
-   Online examination delivery, answer saving and submission.
-   MCQ auto-evaluation and faculty evaluation of descriptive answers.
-   Result preparation, approval and publication.

The system is for a college-level deployment. Do not assume it is an
official Gauhati University platform or that it has direct integration
with Gauhati University systems.

    chunk.

-   Descriptive answer evaluation by assigned faculty.

-   Audit logs for important administrative and examination actions.

3.2 Out of scope unless separately approved

-   Advanced AI or webcam-based proctoring.
-   Biometric attendance.
-   Online payments.
-   Native Android/iOS applications.
-   Direct integration with Gauhati University systems.
-   Automated import from external university portals.
-   Complex analytics beyond essential examination reports.
-   Multi-college SaaS tenancy.
-   AI-based descriptive answer grading.

Keep the architecture extensible, but do not implement these features in
the initial version.

4. User Roles and Permissions

4.1 Administrator

The administrator can:

-   Manage academic sessions and configurable academic structures.
-   Manage programmes, departments, semesters, subjects and papers.
-   Create and manage student and faculty accounts.
-   Manage student academic records and subject registrations.
-   Assign faculty to subjects/papers.
-   Create and configure examinations.
-   Review and confirm eligible-student lists.
-   Generate examination roll numbers and admit cards.
-   Initiate and monitor email delivery.
-   Monitor examination status.
-   Manage result approval and publication.
-   View audit logs and system reports.

Sensitive actions must be logged. Use confirmation steps for destructive
or irreversible operations.

4.2 Faculty / Examiner

Faculty can:

-   View only assigned subjects/papers and authorized examinations.
-   Manage question content where permitted.
-   Review descriptive answers assigned to them.
-   Enter marks and evaluation remarks where configured.
-   Save evaluation progress.
-   Submit completed evaluations.
-   View relevant examination and evaluation summaries.

Faculty must not access unrelated student records, answer scripts or
examinations.

4.3 Student

Students can:

-   Sign in securely.
-   View their profile and academic information.
-   View their registered subjects/papers.
-   View examinations for which they are eligible.
-   Download their own admit cards.
-   Access an examination only during its permitted availability window.
-   Save answers and submit the examination.
-   View submission confirmation and published results.

Students must never be able to view another student’s private profile,
admit card, answers or results.

5. Academic Structure and FYUGP Configuration

Represent academic data in a configurable hierarchy. A suggested
structure is:

-   College
    -   Academic session
    -   Programme
        -   Department or discipline, where applicable
        -   Semester
            -   Subject or course
                -   Paper or offering
                    -   Subject category
                    -   Credits and other configurable academic
                        attributes

Support configurable subject categories such as:

-   Major
-   Minor
-   MDC
-   AEC
-   SEC
-   VAC

These categories are configuration values, not hardcoded assumptions
about which student must take which combination.

Academic data rules

-   A student belongs to a programme and academic session and has a
    semester/current academic status.
-   A student may register for multiple subjects or papers in one
    semester.
-   Student-to-subject/paper registration must be represented
    explicitly.
-   A paper offering should identify the relevant academic session,
    semester and subject/category as applicable.
-   Store paper codes and credit values as configurable data.
-   Do not infer enrollment from programme, department or semester
    alone.
-   Preserve historical academic records when a student progresses to
    another semester.
-   Define how repeat/backlog papers are represented only after the
    college confirms the policy.
-   Record the source and date of important enrollment changes where
    practical.

Critical eligibility rule: A student is eligible for an examination only
when there is a valid, active registration for the exact subject/paper
offering being examined, subject to any additional college-approved
eligibility rules. Semester or department membership alone is
insufficient.

6. Examination Workflow

The intended workflow is:

1.  Administrator creates an examination.
2.  Administrator selects the academic session, programme/semester
    scope, subject category and exact subject/paper offering.
3.  Administrator sets examination type, date, start time, duration,
    marks, instructions and applicable settings.
4.  The eligibility engine identifies students with valid registrations
    for the selected paper offering.
5.  Administrator reviews the eligible-student list and resolves
    exceptions.
6.  After confirmation, the system allocates unique examination roll
    numbers or tokens within the defined scope.
7.  The system generates an individual admit-card PDF for each eligible
    student.
8.  The system emails each admit card to the student’s registered email
    address.
9.  Students sign in and access only examinations for which they are
    eligible.
10. Students answer questions; answers are saved according to the
    autosave strategy.
11. Students submit, or the server automatically closes/submits the
    attempt at the deadline according to the approved policy.
12. MCQ answers are evaluated automatically.
13. Descriptive answers are evaluated by authorized faculty.
14. Results are calculated, reviewed, approved and published.
15. Students can view results after publication.

Each transition must have a defined status and permitted actor. Do not
allow a user to skip required workflow states.

7. Examination Configuration

An examination should support, as applicable:

-   Examination title/name.
-   Academic session.
-   Programme and semester scope.
-   Subject category.
-   Exact subject/paper offering.
-   Examination type: MCQ, descriptive or mixed, if mixed mode is
    approved.
-   Examination date.
-   Start and end time or duration.
-   Maximum marks and pass criteria, if supplied by the college.
-   Question/section configuration.
-   Instructions.
-   Eligibility snapshot or confirmed eligibility record.
-   Status and publication controls.

Do not assume grading, negative marking, pass marks, grace marks,
moderation or revaluation policies. Make these configurable only after
the relevant policy is confirmed.

Suggested lifecycle statuses:

DRAFT → CONFIGURED → ELIGIBILITY_REVIEW → READY → ADMIT_CARDS_GENERATED → SCHEDULED → LIVE → SUBMISSION_CLOSED → EVALUATION → RESULT_REVIEW → PUBLISHED

The exact state transitions should be documented and enforced. Include
cancellation or archival states where needed.

8. Eligibility Engine

Eligibility must be computed on the backend.

The engine must:

-   Identify the exact paper offering selected for the examination.
-   Find students with an active registration for that offering.
-   Apply only additional eligibility rules explicitly configured and
    approved by the college.
-   Exclude inactive, withdrawn or invalid registrations according to
    confirmed policy.
-   Avoid duplicate eligible records.
-   Record when eligibility was calculated and by whom.
-   Allow the administrator to review the list before final
    confirmation.
-   Record approved manual additions/removals with a reason and audit
    entry.
-   Preserve a snapshot of the confirmed eligibility list for the
    examination.

Revalidate eligibility and exam status at the point of exam access. Do
not trust a student ID, roll number or client-side flag sent by the
browser.

9. Examination Roll Number and Admit Card

9.1 Roll number

-   Generate a unique examination roll number for each eligible student
    within the defined examination scope.
-   Define the format only after the college confirms any required
    convention.
-   Prevent duplicate allocation using database constraints.
-   Preserve the mapping between student, examination and allocated roll
    number.
-   Do not expose internal database IDs as examination credentials.

9.2 Secure access credential

A visible roll number is an identifier, not a secret. Do not use the
roll number alone as authentication.

Use a separate secure credential, such as a random PIN or one-time
activation credential, according to the approved login design. Store
only a secure hash of reusable credentials. Never include plaintext
passwords or reusable secrets in ordinary logs.

9.3 Admit card

Each admit card should contain only the required information, such as:

-   College identity and examination title.
-   Student name and approved student identifier.
-   Examination roll number.
-   Programme, semester and subject/paper details.
-   Examination date, time and duration.
-   Examination instructions.
-   Photo/signature or other fields only if the college requires them.

Generate a separate PDF for each eligible student. Verify that each PDF
is associated with the correct student and examination.

9.4 Email delivery

-   Send the PDF to the student’s registered email address.
-   Track queued, sent, failed and retry states.
-   Do not treat a queued message as successfully delivered.
-   Support safe retries without generating duplicate or conflicting
    admit-card records.
-   Keep email delivery logs without storing unnecessary sensitive
    content.
-   Allow authorized administrators to inspect failures and retry
    delivery.

Use a background job mechanism for bulk PDF/email tasks when
appropriate.

10. Authentication and Authorization

Use a unified sign-in system with role-based routing.

The final login experience must support the college-approved identity
method. The initial recommendation is:

-   Admin/faculty/student: registered username or email plus password.
-   Examination access: the student’s account plus the relevant
    examination authorization; if a separate examination PIN is
    required, treat it as an additional credential, not as a substitute
    for backend eligibility checks.

If the college requires roll-number-based login, use roll number plus a
separate secret credential. Never authenticate with a publicly visible
roll number alone.

Security requirements:

-   Hash passwords using a modern password-hashing method supported by
    the backend framework.
-   Use secure session/JWT handling appropriate to the deployment.
-   Enforce role and object-level permissions on every protected API.
-   Rate-limit login and credential verification.
-   Provide secure password reset or administrator-managed recovery.
-   Avoid revealing whether a particular account exists during failed
    login.
-   Use HTTPS in production.
-   Protect against CSRF, XSS, SQL injection and insecure direct object
    references.
-   Keep secrets and environment-specific credentials out of source
    control.
-   Log security-relevant events without recording passwords, PINs or
    tokens.

11. Examination Engine Requirements

11.1 Question types

Initial supported types:

-   MCQ with one correct option.
-   Descriptive/text answer.

A mixed examination may be supported if approved and properly
represented in the examination configuration.

11.2 Attempt handling

-   The server is authoritative for start time, deadline and submission
    status.
-   The frontend timer is informational and must not determine the true
    deadline.
-   Save answers automatically at safe intervals and on relevant
    interactions.
-   Show clear save status to the student.
-   Prevent answers from being modified after submission or deadline
    closure.
-   Handle refresh, temporary network loss and duplicate requests
    safely.
-   Use idempotent submission so repeated submit requests do not create
    multiple submissions.
-   Record attempt start, last activity and final submission timestamps.
-   Provide a clear submission confirmation.

11.3 Security

-   Never send correct MCQ answers to the student-facing client before
    the exam is closed and policy permits it.
-   Students may access only their own attempt and answers.
-   Validate question IDs and answer ownership on the backend.
-   Do not rely on disabled buttons or hidden UI elements for security.
-   Record important examination events in an audit log.

11.4 Deadline behavior

Define and test the exact policy for:

-   A student opening the exam near the deadline.
-   A student losing connectivity.
-   A student submitting at the deadline.
-   Automatic closure when time expires.
-   A request arriving after the deadline.
-   An administrator cancelling or rescheduling an exam.

The backend must enforce the approved policy consistently.

12. Evaluation and Results

MCQ evaluation

-   Evaluate using server-side answer keys.
-   Support configurable marks per question if required.
-   Support negative marking only if explicitly approved.
-   Ensure repeated evaluation does not duplicate marks.

Descriptive evaluation

-   Assign scripts to authorized faculty/examiners.
-   Allow marks and remarks according to the approved marking scheme.
-   Track draft and submitted evaluation states.
-   Prevent unauthorized changes after finalization, except through an
    approved correction workflow.
-   Keep an audit trail of mark changes.

Results

-   Calculate totals and other grade fields only from approved rules.
-   Keep draft/reviewed/approved/published states distinct.
-   Students must not see unpublished results.
-   Record who approved and published results and when.
-   Provide a controlled correction process after publication.
-   Do not invent grade bands, SGPA/CGPA formulas, pass criteria or
    rounding rules. Confirm the applicable college/university policy
    first.

1. Executive Summary & Architecture Principles

The College Online Examination System is designed as a secure,
responsive, and robust Modular Monolith. It supports the Gauhati
University Four-Year Undergraduate Programme (FYUGP under NEP 2020)
academic hierarchy and examination lifecycle.

Key Architectural Principles

1.  Modular Monolith over Microservices: Single deployable codebase with
    strictly decoupled domain applications. Avoids the network latency,
    distributed transaction failures, and operational overhead of
    microservices while maintaining clean boundaries.
2.  Backend-Authoritative Integrity: All business rules, eligibility
    calculations, countdown timers, autosave versioning, mark
    computations, and role permissions are strictly enforced on the
    server. The client is strictly an interactive view.
3.  Explicit Academic State: No student is eligible for an examination
    based on programme, department, or semester alone. Eligibility
    strictly requires an active, approved enrollment in the exact paper
    offering being examined.
4.  Defense in Depth for Security & Privacy:
    -   Multi-tier authentication: Account credentials establish
        identity; separate, hashed Examination PINs authorize live exam
        sessions.
    -   Private storage for all exam assets (admit cards, answer
        uploads); zero public URL access.
    -   Monotonic versioning on autosave to prevent race conditions over
        unstable mobile connections.
    -   Immutable audit logging for all administrative, eligibility,
        evaluation, and publishing events.

Evaluation of Redis and Celery

-   Role: Bulk operations in examination workflows—such as compiling
    1,000 admit-card PDFs, sending 1,000 emails, or evaluating heavy
    batches—cannot run inside a synchronous HTTP request cycle without
    causing gateway timeouts (HTTP 504).
-   Architecture Decision:
    -   Celery with Redis broker is the designated background processing
        engine for batch jobs, cache-based rate limiting (PIN attempts),
        and exam session heartbeat tracking.
    -   To maintain operational simplicity during initial development
        and CI/CD testing, task execution is abstracted through a
        unified interface (TaskQueueService), enabling synchronous eager
        execution (CELERY_TASK_ALWAYS_EAGER = True) in local test
        environments without requiring an active Redis server.

6. Authentication & Authorization Architecture

6.1 Account Authentication vs. Examination Authorization

A strict conceptual and technical boundary exists between Identity
Authentication and Examination Authorization:

1.  Account Authentication (Who you are):
    -   Establishes identity via email/username and salted password
        hash.
    -   Enforces user status: PENDING_VERIFICATION, PENDING_APPROVAL,
        ACTIVE, INACTIVE.
    -   Issues secure HTTP-only session cookie.
2.  Examination Authorization (What you are allowed to enter):
    -   Having an active student account does not permit opening an
        examination.
    -   Access requires fulfilling all five authorization gates:
        1.  Account authenticated as Student with status == ACTIVE.
        2.  Student exists in the locked ExaminationEligibility snapshot
            for this specific exam.
        3.  Examination status is currently LIVE (or SCHEDULED during
            the configured early-access waiting room buffer).
        4.  Entry Window Rules:
            -   New Attempt Initialization: Permitted only when server
                time is within the configured entry window
                [start_time, entry_cutoff_time]. (During the
                early-access buffer
                [start_time - early_access_buffer, start_time], PIN
                verification grants access strictly to the “Waiting Room
                / Instructions Hall”; question papers and attempt timers
                remain locked until start_time).
            -   Active Attempt Resumption: Permitted only for attempts
                with status == IN_PROGRESS when server time is
                 ≤ end_time.
            -   Post-Deadline / Finalized Attempts: Strictly prohibited.
                Attempts marked SUBMITTED or AUTO_CLOSED_DEADLINE are
                permanently locked.
        5.  Correct, unrevoked, unexpired Examination PIN is supplied
            and verified against its salted hash.

8.2 Failure & Recovery Paths

1.  Network Drop During Examination:
    -   Client stores unsaved keystrokes in a private, scoped browser
        cache (exam_cache_{student_id}_{examination_id}_{attempt_id}).
    -   Client-supplied timestamps are never trusted by the server as
        proof of pre-deadline completion.
    -   Autosave worker retries every 10 seconds with exponential
        backoff while connection is down.
    -   UI displays clear persistent status banner:
        ⚠️ Offline - Changes cached locally.
    -   On reconnect prior to the official deadline (end_time), pending
        changes flush to the server with sequence numbers; write
        acceptance is determined strictly by the server’s trusted
        arrival timestamp. UI displays ✅ All answers saved.
    -   If network reconnects after the official deadline, any answers
        cached offline cannot be accepted for write. The attempt is
        closed based strictly on the valid answers received by the
        server on or before end_time.
2.  Accidental Tab Close / System Restart:
    -   Student navigates back to exam URL.
    -   Backend recognizes active ExamAttempt (status == IN_PROGRESS);
        resumes existing attempt only if server time is  ≤ end_time.
    -   Countdown timer reflects remaining server time (no time lost, no
        timer reset).
    -   All previously saved answers and file uploads load immediately
        into the UI.
3.  Deadline Reached & Strict Server-Authoritative Enforcement:
    -   The official examination deadline (end_time) is strictly
        server-authoritative and marks the absolute cutoff for answering
        questions.
    -   Write requests (autosave updates and manual submissions) are
        accepted only when their trusted reverse-proxy arrival timestamp
        is  ≤ end_time.
    -   Requests first received after end_time are rejected for write,
        regardless of any client-side claims or offline timestamps.
    -   Internal processing latency between reverse-proxy receipt and
        WSGI application completion is accommodated (distinguishing
        arrival from processing completion), but network transport
        latency that results in late arrival after end_time does not
        permit late writes.
    -   At or immediately following end_time, any remaining open attempt
        is transitioned to AUTO_CLOSED_DEADLINE, and all write APIs
        strictly reject further modifications.
4.  Email Delivery Failure:
    -   Failed email attempts are captured in AdmitCardEmailQueue with
        error message.
    -   Admin monitor displays failed records; provides single-click
        “Retry Failed Emails” batch action.
    -   Students can always directly download their admit card from
        their authenticated student portal.

9. Examination PIN Design & Security

9.1 PIN Architecture & Generation

-   Scope & Uniqueness: A unique, cryptographically random Examination
    PIN is generated per student per examination
    ((examination_id, student_id) unique constraint).
-   Generation Strategy (CSPRNG): Generated using Python’s secrets
    module (secrets.choice utilizing system OS entropy /dev/urandom),
    producing a 6-character alphanumeric string. Ambiguous glyphs (e.g.,
    0, O, 1, I, l) are explicitly excluded from the character alphabet
    to prevent transcription errors.
-   Storage & Hashing: Plaintext PINs are never stored in the database.
    PINs are hashed immediately upon generation using Django’s standard
    password-hashing framework (PBKDF2PasswordHasher with SHA-256 and
    unique per-record salt, or Argon2). Plaintext is held in memory only
    during immediate admit card rendering or email dispatch, and
    discarded immediately.
-   Separation from Roll Number: The Roll Number is an institutional
    public identifier displayed on admit cards, attendance rosters, and
    answer script metadata. The Examination PIN is a confidential
    authentication secret required solely to unlock the live exam
    interface.

9.2 Verification, Session Creation, and Resumption

-   Session Creation vs. Non-Consumption:
    -   Successful PIN verification does not consume or destroy the PIN
        during an active examination.
    -   Consuming the PIN on first entry would prevent students from
        recovering from common real-world disruptions (accidental
        browser tab closure, browser crashes, system reboots, or network
        disconnects).
    -   Upon successful PIN verification, the backend issues an
        authorized, time-bound, cryptographically signed Examination
        Session Token (or secure HTTP-only cookie) scoped specifically
        to (student_id, examination_id, attempt_id).
    -   The PIN remains valid for session re-entry and attempt
        resumption throughout the examination’s active window
        (start_time to end_time).
    -   Once the attempt is transitioned to SUBMITTED (manual
        submission) or AUTO_CLOSED_DEADLINE (deadline expiration), the
        attempt is locked permanently; subsequent PIN entries are
        rejected.
-   Reconciled Validity Windows:
    -   New Attempt Initialization Window: The PIN is valid to
        initialize a new examination attempt only from start_time up to
        the examination’s configured entry_cutoff_time (e.g.,
        start_time + 15m or start_time + 30m, which can never exceed
        end_time). After entry_cutoff_time, new attempt initialization
        is rejected (HTTP 403 ENTRY_WINDOW_CLOSED).
    -   Early-Access Buffer (start_time - early_access_buffer to
        start_time): Students may verify their PIN early (default: 15
        minutes before start) to authenticate and enter the virtual
        “Waiting Room / Instructions Hall”. However, question payloads
        are withheld and attempts cannot be started until server time
        reaches start_time.
    -   Attempt Resumption Window: For students with an already-started
        IN_PROGRESS attempt, PIN verification permits session resumption
        until end_time.
    -   Strict Expiration at Deadline: PIN validity for all attempts
        strictly expires at end_time. Under no circumstances does the
        PIN authorize a new attempt or grant write access after the
        official examination deadline.

9.3 Rate Limiting, Failed Attempts, and Lockout Policy

-   Proposed Lockout Policy (Subject to Institutional Security Review):
    -   Verification requests are rate-limited per student per
        examination attempt.
    -   Threshold: Maximum of 5 consecutive failed PIN attempts.
    -   Lockout Action: On the 5th failed attempt, the PIN is locked for
        15 minutes, and an alert entry is written to AuditLog.
    -   Progressive Backoff: Subsequent failures after the initial
        lockout period trigger progressive exponential lockouts (e.g.,
        30 minutes).
    -   Institutional Review Note: This policy is proposed as a security
        baseline; the college administration may review and adjust the
        attempt threshold or lockout duration during final operational
        sign-off.

9.4 Administrator Reissue & Revocation Workflow

-   Revocation & Emergency Reissue:
    -   If a student is locked out due to repeated failures, suspects
        PIN compromise, or loses access, a college administrator can
        reissue the PIN from the Admin Examination Dashboard.
    -   The re-issue operation:
        1.  Marks the existing ExaminationPIN record as revoked
            (is_revoked = True).
        2.  Generates a fresh cryptographically random PIN and stores
            its salted hash.
        3.  Records an immutable entry in AuditLog capturing
            administrator_id, student_id, examination_id, timestamp, and
            administrative justification.
        4.  Provides the new PIN to the administrator for direct
            delivery or triggers a secure notification to the student.

9.5 Protection Against Disclosure in Logs & APIs

-   Zero Plaintext Logging: Plaintext PINs are strictly excluded from
    Django application logs, web server access logs (via POST body
    submission, never URL parameters), and AuditLog change payloads.
-   API Protection: No API endpoint ever exposes stored PIN hashes or
    plaintext PINs. Verification endpoints return only boolean
    verification status and ephemeral session tokens.

10. Roll-Number Architecture

10.1 Configurable Format Generator (Illustrative Only)

  [!IMPORTANT] The pattern below is strictly illustrative to demonstrate
  the generator’s template architecture. It is not an approved college
  format or an authoritative system default. The actual roll-number
  format must be configured by college administrators once the official
  Gauhati University or institutional convention is supplied.

The roll-number engine is completely configurable and avoids any
hardcoded numbering conventions:

    # Conceptual Roll Number Template Engine
    class RollNumberScheme(models.Model):
        name = models.CharField(max_length=100) # e.g. "College FYUGP Examination Format"
        # Illustrative pattern only; fully configurable with parameters:
        # {COLLEGE_CODE}, {YEAR}, {SESSION}, {PROG_CODE}, {DEPT_CODE}, {SEMESTER}, {SEQUENCE:04d}
        pattern = models.CharField(
            max_length=255, 
            help_text="Customizable pattern template using dynamic parameters"
        )
        sequence_start = models.PositiveIntegerField(default=1)
        current_sequence = models.PositiveIntegerField(default=1)
        scope = models.CharField(max_length=50, choices=[
            ('PER_EXAM', 'Per Examination Instance'),
            ('PER_SESSION_PROGRAMME', 'Per Academic Session and Programme'),
            ('PER_COLLEGE_ANNUAL', 'College-Wide Annual Sequence')
        ])

10.2 Concurrency, Uniqueness & Administration

-   Transaction-Safe Atomic Sequence Allocation: Roll numbers are
    allocated in bulk during the transition from ELIGIBILITY_REVIEW to
    READY. Allocation runs inside an atomic database transaction using
    row-level locking (SELECT ... FOR UPDATE on the RollNumberScheme
    sequence counter) to guarantee sequential ordering without duplicate
    sequence gaps or collisions.
-   Database Integrity Constraints: Database-level composite unique
    constraint enforces uniqueness:
    -   Scoped to (examination_id, roll_number) or
        (academic_session_id, roll_number) depending on the configured
        scheme scope.
-   Administrator-Controlled Corrections & Re-issues:
    -   If a student is added late (manual eligibility addition) or an
        allocation error occurs, administrators can re-allocate or
        manually assign a corrected roll number.
    -   Manual overrides require an administrative justification note
        and generate an immutable record in AuditLog preserving the
        previous number, the new number, and the authorizing
        administrator.
-   Historical Immutability: Once admit cards are compiled and
    published, the roll-number mapping is locked permanently for that
    examination attempt to preserve historical examination records.

11.3 Multi-Tier Validation & Malware Protection

1.  Client-Side Preliminary Validation: React exam interface validates
    file extension and size prior to network transmission, providing
    immediate student feedback without wasting uplink bandwidth.
2.  Server-Side Whitelist Enforcement: File extension is checked against
    the active examination configuration whitelist.
3.  MIME-Type & Magic-Byte Signature Inspection: Using binary signature
    inspection (python-magic or header byte analysis), the server
    verifies the actual binary content matches legitimate PDF, JPEG, or
    PNG formats, rejecting renamed executable binaries, PHP scripts, or
    shell payloads.
4.  Pluggable Malware Scanning Interface: The architecture provides a
    pluggable antivirus hook (supporting ClamAV daemon via TCP/Unix
    socket). When enabled in production, files are streamed to the
    scanner before committing to disk; infected files are discarded
    immediately and logged in AuditLog.

11.4 Private Storage & Controlled Access

-   Private Storage Outside Webroot: Stored in
    MEDIA_ROOT/private/descriptive_uploads/{exam_id}/{attempt_id}/. Web
    server configurations explicitly block direct URL alias access to
    this path.
-   Randomized UUID Filenames: Original client filenames (which may
    contain path traversal characters or malicious naming) are stripped;
    files are saved exclusively as uuid4() identifiers.
-   Authenticated Download Endpoint:
    -   GET /api/attempts/{attempt_id}/uploads/{upload_id}/download/
    -   Access is granted only if:
        1.  Caller is the authenticated student who owns the attempt, OR
        2.  Caller is the faculty examiner assigned to evaluate this
            paper offering, OR
        3.  Caller is an authorized college administrator.
    -   In production, files are delivered efficiently via Nginx
        X-Accel-Redirect (or Django FileResponse in development),
        eliminating Python memory overhead.

11.5 Retention & Archival Policy Considerations

-   Active Retention: Uploads must be retained in active
    high-performance storage throughout the live examination,
    evaluation, result compilation, and re-evaluation appeal windows
    (typically 6 months post-publication).
-   Archival vs. Purging: Following the expiration of the appeal period,
    the system supports an automated archival job to bundle scripts into
    compressed cold storage or permanently purge files per college
    statutory document retention regulations. Specific retention
    schedules require institutional policy confirmation.

13. Examination Reliability & Integrity Architecture

13.1 Server-Authoritative Timer & Trusted Arrival Deadline Policy

-   Zero Trust in Client Timestamps:
    -   Client/browser timestamps are never trusted by the server as
        proof that an answer was entered or submitted before the
        deadline. A compromised client, manipulated system clock, or
        modified script could trivially forge pre-deadline timestamps.
    -   The server’s clock and trusted network gateway timestamps govern
        all deadlines.
-   Trusted Reverse-Proxy Arrival Timestamp:
    -   The authoritative time of request receipt is established
        strictly by the trusted reverse proxy (e.g., Nginx $time_iso8601
        or $msec), captured at the instant the request arrives from the
        network.
    -   Nginx unconditionally overwrites and forwards this value to the
        backend in a protected server header (e.g.,
        X-Request-Arrival-Time).
    -   Fallback Mechanism: If the deployment environment lacks a
        configured trusted reverse proxy (or during local direct WSGI
        execution), the strict fallback is the server-receipt cutoff
        timestamp captured at the WSGI entry point (time.time()) upon
        socket read.
-   Strict Cutoff on Request Arrival (No Late Writes):
    -   A write request (autosave update or submission) is accepted only
        when its trusted arrival timestamp is at or before the official
        scheduled deadline:
        T_(arrival) ≤ official_end_time
    -   Any request whose trusted arrival time is  > official_end_time
        must be rejected for answer writes. No client-side explanation,
        transport excuse, or offline timestamp permits accepting answers
        that arrive after the deadline.
-   Distinction Between Request Arrival and Processing Completion:
    -   If a request physically arrives at the trusted reverse proxy
        before the deadline (T_(arrival) ≤ official_end_time), but
        backend worker thread scheduling or database lock contention
        causes processing to complete slightly after
        (T_(complete) > official_end_time), the write is accepted and
        committed because the request was verified to have arrived on
        time.
    -   The internal latency buffer accommodates server processing
        queues, but never extends answering time or permits
        late-arriving requests.
-   Exact Handling of Requests at the Deadline:
    1.  Autosave Arriving On or Before Deadline
        (T_(arrival) ≤ end_time):
        -   Verified against monotonic sequence version
            (incoming_seq > stored_seq).
        -   Answer updated in database; returns HTTP 200 with server
            timestamp.
    2.  Autosave Arriving After Deadline (T_(arrival) > end_time):
        -   Write operation is rejected immediately with HTTP 410
            (EXAMINATION_CLOSED).
        -   Answer payload is discarded. The attempt is transitioned to
            AUTO_CLOSED_DEADLINE if not already finalized.
    3.  Submission Arriving On or Before Deadline
        (T_(arrival) ≤ end_time):
        -   Atomic transaction locks attempt, transitions
            status = SUBMITTED, sets submitted_at = T_arrival.
        -   Automatically invokes MCQ auto-grading and returns a signed
            submission receipt.
    4.  Submission Arriving After Deadline (T_(arrival) > end_time):
        -   Manual submission write is rejected.
        -   Atomic transaction checks attempt state; if IN_PROGRESS,
            transitions status = AUTO_CLOSED_DEADLINE, sets
            closed_at = official\_end\_time.
        -   Invokes MCQ auto-grading on all answers successfully saved
            on or before end_time.
        -   Returns a submission receipt reflecting that the examination
            was closed at the deadline.
    5.  Network Interruptions Across the Deadline:
        -   If a student disconnects before the deadline and reconnects
            afterward, any answers entered into the local offline cache
            after end_time cannot be accepted.
        -   Upon reconnection, the client receives HTTP 410 informing
            the student that the exam has closed; the attempt is
            finalized using only the answers synchronized prior to
            end_time.

13.2 Autosave Strategy & Monotonic Sequence Versioning

-   Heartbeat & Trigger Events: Answers autosave periodically (default:
    every 30 seconds) and immediately upon field blur or question
    palette navigation.
-   Monotonic Sequence Versioning:
    -   Every answer update includes a client incremented sequence
        counter: { question_id: 101, answer: "...", sequence: 14 }.
    -   The server verifies:
        IF payload.sequence > existing_answer.version_sequence THEN UPDATE.
    -   Stale payloads arriving out of order due to network jitter or
        packet retransmission are safely discarded without overwriting
        newer state.

13.3 Offline Cache Architecture, Privacy & Cleanup Lifecycle

To ensure data integrity during transient network drops while strictly
protecting candidate privacy on shared devices (such as college computer
labs and commercial cyber cafes), offline caching adheres to the
following lifecycle rules:

1.  Scoped Storage Namespacing:
    -   Cached answers are stored in browser storage (localStorage /
        IndexedDB) using strictly scoped, collision-proof keys:
        cache_key = exam_cache_{student_id}_{examination_id}_{attempt_id}
    -   Global, un-scoped keys (e.g., saved_answers) are strictly
        prohibited to prevent data contamination between consecutive
        candidates using the same workstation.
2.  Strict Zero-Credential Caching:
    -   User account passwords, Examination PINs, session cookies, and
        authorization tokens must never be stored in browser offline
        caches or local storage.
3.  Preservation of Unsynchronized Answers:
    -   Keystrokes and selections cached offline are preserved locally
        until and only until the backend server returns an explicit HTTP
        200 response acknowledging the sequence number.
    -   The client never purges or overwrites unsynchronized answers
        prior to successful server acknowledgement.
4.  Immediate Cleanup on Confirmed Finalization:
    -   As soon as the client receives a confirmed submission receipt or
        an AUTO_CLOSED_DEADLINE response acknowledging attempt
        finalization, the entire attempt cache (exam_cache_*) is
        immediately deleted.
5.  Cleanup on User Logout & Shared-Device Protection:
    -   When a user clicks “Logout”, an automated cache cleanup routine
        purges all exam_cache_* keys stored on the device.
    -   If unsynchronized answers exist at the moment of logout, the
        student is prompted with an explicit confirmation modal:
        ⚠️ You have unsaved examination answers. Logging out now will permanently discard them. Please wait for reconnection or submit before exiting.
6.  Time-To-Live (TTL) & Stale Cache Eviction:
    -   All cached attempt data carries a client-side TTL set to the
        examination’s scheduled end_time.
    -   Once the local device clock or server heartbeat exceeds
        end_time, any remaining cached data for that attempt is
        automatically purged to prevent subsequent users of the device
        from viewing past examination answers.

13.4 Idempotent Submissions

-   When the student submits or the server auto-closes the exam:
    -   Frontend generates a unique submission_uuid.
    -   Backend wraps attempt completion in an atomic transaction:
        1.  Lock ExamAttempt row (SELECT ... FOR UPDATE).
        2.  Check if already SUBMITTED or CLOSED. If so, return existing
            submission receipt immediately without re-executing scoring.
        3.  Mark status = SUBMITTED, submitted_at = now().
        4.  Trigger automatic MCQ scoring pipeline.
        5.  Return submission receipt.

15. Auditability, Security & Privacy

15.1 Centralized Audit Trail

1.  Comprehensive Event Logging: Every critical state transition
    (Enrollment approval, Eligibility override, Roll generation, PIN
    reissue, Mark change, Result publication) records:
    -   actor_id (User who performed the action).
    -   action_type (e.g., ELIGIBILITY_OVERRIDE, MARK_MODIFIED,
        PIN_REISSUED).
    -   target_model & target_id.
    -   previous_state & new_state (JSON diff).
    -   ip_address & user_agent.
    -   timestamp (UTC).
2.  Secret Hygiene: Audit payloads strictly scrub passwords, plain PINs,
    and session tokens.
3.  Data Protection: Student personal data, admit cards, and answer
    sheets are accessible strictly by authorized personnel via
    authenticated endpoints.

15.2 Cross-Site Scripting (XSS) Defenses & Session Hardening

  [!SECURITY] Accurate Security Boundary Statement: The system does not
  claim that HTTP-only cookies provide “complete” or “total” protection
  against XSS. While the HttpOnly flag successfully prevents client-side
  JavaScript from directly reading document.cookie (stopping direct
  credential exfiltration), it does not prevent an attacker who
  successfully executes arbitrary script from issuing authenticated
  same-origin requests (“session riding”) on behalf of the candidate.
  Comprehensive defense-in-depth is therefore required and enforced.

To defend against XSS and protect session integrity, the architecture
enforces multiple defense layers:

1.  Context-Aware Output Encoding & Safe Templating:
    -   React JSX inherently escapes values before rendering,
        neutralizing standard HTML and script injection vectors.
    -   Raw HTML injection points (e.g., dangerouslySetInnerHTML) are
        strictly prohibited in user-facing views; any rich-text
        rendering is sanitized using DOMPurify.
2.  Strict Content Security Policy (CSP):
    -   Nginx and Django django-csp headers enforce a strict policy:

            Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; object-src 'none'; frame-ancestors 'none'; base-uri 'self';

    -   Restricts script execution strictly to same-origin application
        bundles; completely disallows inline scripts (unsafe-inline in
        script-src) and script evaluation (unsafe-eval).
3.  Input Validation & Sanitization:
    -   All incoming textual payloads (student registration inputs,
        descriptive answers, remarks) are validated and sanitized on the
        backend using Django serializer validators.
4.  Dependency Security Auditing:
    -   Automated CI vulnerability scanning via npm audit for frontend
        libraries and pip audit / safety for Python packages to guard
        against supply-chain vulnerabilities.
5.  Session Hardening & CSRF Protection:
    -   Session cookies are configured with HttpOnly=True,
        SameSite='Lax' (or 'Strict'), and Secure=True (HTTPS).
    -   Combined with Django’s double-submit CSRF tokens (X-CSRFToken)
        on all non-GET requests to prevent cross-site forged
        transactions.

3. Architecture Summary

The system is designed as a Modular Monolith engineered for high
integrity, college-level deployment, and strict compliance with Gauhati
University FYUGP academic structures:

1.  Frontend Architecture:
    -   React 18+ SPA built with Vite and Tailwind CSS.
    -   Domain-separated feature modules (auth, student, exam-interface,
        faculty, admin-academics, admin-students, admin-enrollment,
        admin-exams, admin-results, admin-audit).
    -   Role-based route guards (PublicOnlyRoute, ProtectedRoute,
        RequireRole, LiveExamGuard).
    -   Centralized Axios client with automatic CSRF tokens
        (X-CSRFToken), HTTP-only session cookies, strict CSP, and scoped
        offline network resilience.
2.  Backend Architecture:

6. Security & Privacy Review

1.  Authentication & XSS Defense-in-Depth:
    -   Cookies configured with HttpOnly, SameSite=Lax (or Strict), and
        Secure=True.
    -   Accurate Scope: The architecture clearly documents that HttpOnly
        mitigates raw cookie theft but does not prevent XSS from issuing
        authenticated requests on behalf of the user.
    -   Comprehensive multi-layer protection: React JSX output escaping,
        strict CSP blocking inline scripts and unauthorized hosts,
        backend input validation, dependency security auditing, and CSRF
        tokens on all state-changing endpoints.
2.  Examination PIN Security & Lifecycle:
    -   Generated using cryptographically secure random entropy
        (secrets.choice / /dev/urandom).
    -   Salted hashing (PBKDF2-SHA256 / Argon2) ensures zero-knowledge
        database security.
    -   Verification creates an ephemeral signed session token rather
        than consuming/destroying the PIN, ensuring resilience against
        mid-exam disconnects or browser crashes while preventing
        post-submission reuse.
    -   Reconciled entry windows prevent new attempt creation after
        entry_cutoff_time and prevent PIN use after end_time.
    -   Rate limiting (5 failed attempts before 15-minute lockout) is
        documented as a proposed policy subject to college sign-off.
    -   Administrative reissue is fully auditable with mandatory
        justification.
    -   Plaintext PIN is strictly excluded from AuditLog, application
        logs, and API responses.
    -   Delivery method is unconfigured by default, requiring explicit
        administrator approval before PIN issuance.
3.  File Upload Security & Malware Defense:
    -   Multi-layer defense: Configurable extension whitelist, MIME-type
        validation, and binary magic-byte inspection (detecting
        disguised PHP, shell scripts, or executable binaries).
    -   Pluggable malware scanning interface (ClamAV) to scan incoming
        streams before committing to disk.
    -   Filename sanitization: Client filenames are completely replaced
        with random UUIDs (uuid4()).
    -   Private media storage: Placed completely outside the public web
        root; accessed strictly via authenticated controller endpoints
        with role and ownership checks.
4.  Offline Cache Privacy & Shared-Device Safety:
    -   Cache keys strictly scoped to
        (student_id, examination_id, attempt_id).
    -   Credentials (passwords, PINs, tokens) strictly prohibited from
        browser caches.
    -   Immediate cache deletion on confirmed submission or auto-close
        acknowledgement.
    -   Cache purge on logout with unsaved warning, plus client-side TTL
        eviction at end_time, preventing data leakage on shared
        computers in college labs or cyber cafes.
5.  Audit Trail & Secret Hygiene:
    -   Centralized AuditLog records actor, IP address, action, target
        entity, and before/after state diffs.
    -   Passwords, plain PINs, and auth tokens are explicitly scrubbed
        from audit payloads and application logs.

7. Reliability, Scalability & Concurrency Review

1.  Autosave Race Conditions: Monotonic sequence versioning
    (WHERE sequence < incoming_sequence) eliminates race conditions
    caused by delayed packets over mobile networks.
2.  Concurrent Roll-Number Allocation: Database row locks
    (SELECT ... FOR UPDATE) guarantee zero duplicate sequence numbers
    even during high-concurrency batch allocations.
3.  Strict Server-Authoritative Deadline Integrity:
    -   Zero trust in client timestamps.
    -   Requests arriving before end_time at the trusted reverse proxy
        are accepted even if internal processing finishes slightly after
        end_time.
    -   Requests first received after end_time are rejected immediately
        with HTTP 410, and attempt is transitioned to
        AUTO_CLOSED_DEADLINE.
    -   Offline answers entered after end_time cannot be synchronized
        upon reconnection; attempt is finalized using only pre-deadline
        saved state.
4.  Peak Examination Traffic:
    -   Read-heavy live exam questions and configuration can be cached
        in Redis.
    -   Static assets served directly by Nginx.
    -   Autosave requests are lightweight (PATCH with minimal payload),
        minimizing database I/O.
5.  Idempotent Exam Submission: Atomic database locking on submission
    prevents double-submission or duplicate evaluation triggers if
    students double-click the submit button.
